Connected spines

The Python lanes move in sequence, not by coincidence

The backend reads more clearly once each file is placed in the motion it actually supports. connectors.py begins the evidence path, pipelines.py turns rows into multimodal events, service.py keeps the runtime edge composed, and the review lanes decide what is safe to keep, replay, retire, or question.

01 · intake and shape
connectors.py catalog.py catalog_store.py

These modules decide what arrived, how the fields were typed, and whether a dataset contract can be named before the rows are pushed deeper into the system.

02 · pair and measure
pipelines.py quality.py signal_math.py alignment.py

This is where rows become timed modality events and where entropy, sparsity, alignment, and evidence windows are measured instead of assumed.

03 · infer and persist
contracts.py service.py retrieval.py video.py job_store.py

The central service keeps inference, retrieval, video cleanup, and async jobs on the same contract spine so the runtime does not splinter into separate mini apps.

04 · review and attest
drift.py domain_ontology.py liability_surface.py stewardship_store.py proof.py

The later lanes answer a different question: not only can this run, but also what changed, what moved, what aged out, and what should leave an audit mark before it is trusted.

Math spine

Signals the runtime keeps close

The measurement layer is small on purpose. Each signal is simple enough to test and strong enough to keep weak data from becoming a confident answer.

Entropy and sparsity quality.py + signal_math.py
Pairwise alignment windows alignment.py + pipelines.py
Provenance and replay match provenance.py + replay.py
Lifecycle and drift posture drift.py + stewardship_store.py
These bars are not vanity scores. They name the exact places where the repository decides whether a signal can stay in motion or needs another look first.
Why the files stay separate
api.py → service.py proof.py → readiness.py export_openapi.py → sdk/*

The separation is part of the discipline. The API edge should not know how SQLite rows are stored. The math lane should not know how a client SDK is packaged. The proof lane should be able to count what exists without pretending to be the runtime itself.

That is why the same repository can explain itself to a researcher, a backend engineer, and an integration team without flattening every concern into one oversized script.

Runtime posture

What changed in the codebase

The earlier repository kept its research archive and runtime edge too close together. The current spine gives each layer a clearer place.

  • A package-backed runtime now lives in src/advanced_multimodal_ai.
  • Inference can be planned before it runs, not only observed afterward.
  • Retrieval has an actual backend path instead of only a concept.
  • Dataset schemas can be versioned, fingerprinted, and compared before a pipeline shifts in production.
  • Public web intake now respects allowlists, robots checks, byte caps, and request spacing.
  • Quality, provenance, and timed alignment now sit beside inference instead of outside it.
  • Population-entry drift can be checked before a new cohort is folded into a stable lane.
  • Enterprise artifacts can be compiled into ontology snapshots and compared against live traces.
  • The video lane works with transcripts, frame signals, and audio energy rather than vague captions.
