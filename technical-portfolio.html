Python weave

Why these files lean on one another

The Python package is easier to trust once the files are read as lanes of one system. Intake, measurement, orchestration, and review are kept apart so each part can be tested without turning the repository into a single oversized script.

Intake path

Rows arrive before tensors do

connectors.py connector_store.py catalog.py catalog_store.py pipelines.py

These files stay together because one typed pull should be able to do three things at once: bring the rows in, describe them as a dataset contract, and map them into persisted pipeline work without asking for a separate preparation script.

The intake lane answers three questions in order: what arrived, how was it typed, and what multimodal batch should be built from it next.
Measurement path

Weak signals are named early

quality.py signal_math.py alignment.py provenance.py replay.py

This group stays separate from inference because entropy, sparsity, temporal alignment, and provenance need to remain inspectable on their own. The repository should be able to say why a signal looked fragile, not just that a model happened to be uncertain.

A replay only matters if the earlier receipts and timing windows were kept intact. That is why provenance and replay share a lane.
Runtime path

Contracts hold the center

contracts.py service.py retrieval.py video.py api.py

The central service composes the runtime edge, but it does not own everything. Contracts define the shapes, service coordinates the work, retrieval keeps memory bounded, video handles temporal cleanup, and the API stays narrow enough to expose the work without duplicating it.

The service exists to keep these capabilities in one runtime, not to flatten them into one file.
Review path

Change, drift, and liability remain visible

drift.py drift_store.py domain_ontology.py liability_surface.py stewardship_store.py readiness.py

These files answer a different class of question. Not what the model predicted, but what moved, what aged out, what crossed a boundary, and which datasets still lack a clean review rhythm.

Readiness becomes more useful once it can see lifecycle policy, drift baselines, supply paths, and route evidence in one place.
Math lanes

Small measures with operational weight

The repository does not need decorative numerics. It needs a handful of measures that change how data is handled before it becomes another glossy output.

Entropy and sparsityquality.py
Pairwise alignmentalignment.py
Schema fingerprintingcatalog.py + rust_bridge.py
Each measure is tied to a real decision: whether to fuse, whether to replay, whether to accept a schema change, or whether a new cohort should pause for review.
Delivery path

One contract, several surfaces

attestation.py proof.py scripts/export_openapi.py sdk/python sdk/typescript

The public surface should be able to explain itself without hand-written divergence. The proof lane counts what exists, the OpenAPI export freezes the live contract, and the generated clients keep the downstream Python and TypeScript surfaces aligned with it.

That is how the repository stays legible across code, documentation, and front-end pages without pretending they are separate stories.
contracts

`contracts.py`

Tensor payloads, retrieval schemas, quality reports, provenance receipts, temporal alignment windows, video packet schemas, and benchmark results all live here.

service

`service.py`

The coordination layer for contract inference, research fallback, retrieval, metrics, quality profiling, provenance, video cleanup, and stream events.

rust core

`crates/multimodal-core`

A compiled lane for deterministic tensor signatures and transcript-led temporal cuts.

retrieval

`retrieval.py`

Memory index by default. Qdrant path when the environment is ready.

video

`video.py`

Transcript grouping, silence gap detection, filler word cuts, retained spans, and evidence packet assembly.

data quality

`quality.py` and `signal_math.py`

Shared tensor summaries, modality health checks, fusion-readiness scoring, and pairwise alignment readings.

tensor guard

`tensor_guard.py`

A pre-inference intercept lane for entropy, spatial frequency, saturation, and risk scoring before a restricted modality reaches inference.

drift

`drift.py` and `drift_store.py`

Reviewed population baselines, modality-level drift deltas, alignment drop, and persisted baseline records.

connectors

`connectors.py` and `connector_store.py`

Typed row pulls for local CSV, local Parquet, S3-backed Parquet, local NDJSON, HTTP JSON, HTTP NDJSON, and public HTML pages, plus persisted ingest benchmarks.

recipes

`recipes.py` and `recipe_store.py`

Compiled manifests with dataset-resolution evidence, launch topology, export commands, and persisted handoff records.

pipelines

`pipelines.py` and `pipeline_store.py`

Raw event pairing into aligned inference batches, persisted run records, and dropped-event accountability.

replay

`replay.py`

NDJSON lineage export, deterministic artifact digests, and replay comparison for saved pipeline runs.

provenance

`provenance.py` and `alignment.py`

Deterministic payload receipts and timed observation grouping for cross-modal corroboration.

ontology

`domain_ontology.py`, `liability_surface.py`, and `ontology_store.py`

Enterprise artifact ingestion, compiled governance constraints, live trace comparison, and persisted ontology snapshots.

stewardship

`stewardship_store.py` and `service.py`

Persisted lifecycle policies, change-control records, supply-chain snapshots, and one posture surface for review coverage and data retirement.

bias

`bias_taxonomy.py`

A sixty-category register for where bias enters a system, plus a stage-aware assessment lane.

job lane

`job_store.py`

A persisted SQLite-backed lane for longer-running video cleanup and multimodal batch inference work.

registry

`registry.py` and `legacy.py`

The bridge between the new runtime edge and the older research model files already present in the repo.

sdk

`sdk/typescript`

A small client for health checks, stewardship surfaces, quality, provenance, planning, inference requests, alignment windows, and the WebSocket stream.

operations

`Dockerfile`, `compose.yaml`, `monitoring/`, and `sql/runtime_schema.sql`

Local container bring-up, Prometheus scrape configuration, explicit runtime tables, and a concise operations path.

openapi

`scripts/export_openapi.py` and `scripts/generate_sdk_surfaces.py`

The runtime can export its own contract and regenerate Python and TypeScript client surfaces from that document.

readiness

`readiness.py` and `scripts/export_readiness_report.py`

A typed report that keeps route count, test count, connector coverage, recipe evidence, and operating boundaries together in one inspectable surface.
